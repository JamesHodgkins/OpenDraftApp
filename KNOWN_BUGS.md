13. ~~Offset didn't complete when finishing by clicking the viewport (typing values worked); after a follow-up fix, it would complete on one side but not the other.~~ — Fixed, two parts:
    - **Couldn't finish by clicking at all:** Offset's flow is `distance` → `mode` ("both"/"pick side", a `choice` export) → `side_point` → commit. A canvas click can never answer a `choice` export (`Editor.provide_point` just shows a "type B/P" hint and swallows it, per #6/#16 above) — so after clicking to set the distance, the natural next click (picking a side to finish) did nothing. Added `StatefulCommandBase.handle_choice_click(name, pt)`, an opt-in hook `Editor.provide_point` calls before falling back to the hint; `OffsetCommand` implements it so a click during the `mode` step means "pick side" *and* supplies that point as `side_point` in one gesture — matching the natural two-click workflow, while typing `B`/`P` still works as before. See `app/editor/stateful_command.py`, `app/editor/editor.py::provide_point`, `app/commands/modify_offset.py::OffsetCommand.handle_choice_click`.
    - **Completed on one side but not the other:** two separate bugs compounded. First, `OffsetCommand.commit()` returned `None` (implicit) on every early-return guard (invalid distance/mode/side, or no valid offset results) rather than `False` — but `Editor.commit_command()` only keeps a command running when `commit()` returns exactly `False`; `None` reads as "finished" and tears the command down (`_finish_stateful`), so any guard firing — from an auto-commit or a manual Enter — silently killed the whole command instead of leaving it running to correct. Second, a distance click landing on (or a hair from) the selected geometry measured ~0, which still advanced past the `distance` step (`0.0 is not None`) but then could never auto-commit (`all_exports_set()` requires `distance > 0`) no matter which side was picked afterwards — a silent stall with no explanation, until some other action (e.g. Enter) hit `commit()`'s now-fixed guard and quit the command, which is what "works on one side, not the other" looked like from the outside. Fixed by returning `False` from every `commit()` guard, and by adding `StatefulCommandBase.reject_point(name, pt)` — a hook to veto a click outright (distinct from `value_from_point` returning `None`, which just falls back to generic per-`input_kind` handling, e.g. raw distance-from-origin for a `length` export — actively wrong here) — which `OffsetCommand` uses to reject a ~0 measured distance with a status message instead of accepting it. See `app/commands/modify_offset.py::OffsetCommand.commit/reject_point`, `app/editor/stateful_command.py`, `app/editor/editor.py::provide_point`. Regression tests: `tests/test_modify_offset.py::test_offset_two_viewport_clicks_complete_without_typing_mode`, `::test_offset_commit_failure_keeps_command_alive_instead_of_quitting`, `::test_offset_distance_click_on_the_geometry_itself_is_rejected`.
    - **Still failed after all of the above — typing the distance (not clicking it), then clicking a side, silently ate the first click and then "reset" on the second:** the real culprit was `set_stateful_property`'s click-suppression flag from #11 (`_suppress_next_click_point`). It arms whenever a `point`/`vector`/`length`/`angle` export is committed through that path — necessarily speculatively, since nothing there can tell a click's own focus-out commit apart from a deliberate Enter/Space commit with no click involved at all. #11's fix armed it with no expiry, relying on *some* click eventually consuming it — which works when that click is the same one that caused the focus-out, but means a plain Enter/Space commit (typing the distance and pressing Enter, no click involved) left it armed indefinitely, silently swallowing the *next*, entirely unrelated click — here, Offset's side-pick click. That click did nothing (the eaten one), and whatever the user tried next (another click, Enter) finally hit `commit()`'s "click to indicate which side" guard, which (now correctly) returns `False` — but by then it reads as the command having done nothing and gotten stuck, matching "no status message but the command just resets." Fixed by expiring the flag on the next event-loop tick (`QTimer.singleShot(0, ...)`) instead of leaving it armed indefinitely: a genuine same-gesture click's point delivery always happens synchronously within the same call stack as the focus-out that armed the flag (`CADCanvas.mousePressEvent` triggers the focus-out, *then* delivers its own point, all before returning), so it's always consumed before the next tick; an Enter/Space commit has no such click coming, so the flag now correctly clears itself before some later, unrelated click can wrongly eat it. See `app/editor/editor.py::set_stateful_property`. Regression test: `tests/test_canvas.py::test_stale_click_suppression_does_not_eat_a_later_unrelated_click`.
